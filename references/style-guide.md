# 默认作者的语言风格

这份参考只负责 Sincerelyplz 默认风格的语气、节奏和排版。是否采用默认风格，由 [主文件](../SKILL.md) 决定；用户样本分支不叠加本文件。事实、经历和交付范围也以主文件为准。

## 语气与作者声音

像一名后端工程师把问题和取舍讲给同行听，平实、具体，专业名词保持准确。

- 作者声音体现在解释角度、证据选择和取舍依据上；直接说明机制及其适用条件，也可以有鲜明的行文风格。
- 第一人称可用于有依据的理解、疑问和条件性取舍，真实经历按主文件确认归属。不要求每篇有个人故事，也不为每章补一句个人表态。
- 口语自然即可。默认作者不喜欢长段反问、连续设问和自问自答；直接陈述事实、机制和判断。不把固定口头禅、热梗或“狗头”当成风格标记。
- 问题直接落到对象和动作上。需要强调时，让事实和后果承担分量，不替读者预判它多么重要。
- 保留材料中已经自然的用词；不为模仿作者而增加粗口、玩笑或额外情绪。

## 句子与段落

- 一段围绕一个判断展开，长短由信息决定。解释机制可以稍长，提出疑问或改变方向可以短。
- 中短句为主。遇到多层条件和因果时拆开，让读者能跟住动作和前提。
- 句子的主语尽量落在人、系统、请求或数据上，用它们做了什么表达变化。
- 前后句有承接，段落不追求等长；也不把每句话都拆成单独一段。
- 允许术语自然重复，不为避免重词给同一技术对象轮换名称。
- 修改病句和歧义，保留口语的松紧，不把全文抛光成论文腔。

## 直接陈述，避免连续设问

这是默认作者明确提出的写作偏好，适用于技术博客的正文、列表和章节引导。不要用长段反问、连续设问或“为什么？因为……”引出本来可以直接说清的内容。即使没有问号，“要不要……哪些……什么时候……”也可能只是把几个问题塞进陈述句。

改写时直接说明主体、动作、对象和收益：能控制什么，就写控制什么；需要配置什么，就列配置项。不能只删问号，也不要把未验证的问题改成已确定的结论。真实用户提问、引文和确有必要保留的研究问题不机械改写；短标题可以概括真实问题，但正文不再复问一遍。

**示例一：控制能力与调试收益**

不采用：

> 中间要不要继续调用、哪些结果写进上下文、什么时候开始合成，应用都有明确的处理位置。这也是级联容易拆开调试的原因。

采用：

> 通过级联的方式，我们可以处理中间的调用结果，选择写入上下文的内容，并控制语音合成的时间点。这样方便调试，出了错也可以按语音识别、模型与工具调用、语音合成几个环节分别排查。

**示例二：需求列表**

不采用：“供应商的地址、密钥，统一在哪里维护？哪些用户能使用哪些模型？预算和消费记录，怎么分配到具体的人？”

采用：“统一维护供应商的地址和密钥，按用户配置模型访问权限，并把预算和消费记录绑定到具体用户。”

这些例子用于约束句式，不要求其他文章照搬 Voice Agent 的内容。“比较直观”“这条路线很直观”也不作为解释前的过渡，直接写“级联的实现包含以下三个部分”等具体内容。

## 解释密度与章节分工

- 概念介绍与项目落地按已确认的章节职责展开；通用原理章节不自动塞入“我们项目”的实现。讲架构时优先交代职责、数据流和取舍，未要求时不罗列具体接口、请求字段或调用步骤。
- 同一概念确定一个主要解释位置。定义、职责和直接收益可以放在一起，不把同一个观点拆成多个小节反复说明；后文引用它时，只交代当前新增的关系。
- 问题驱动不等于每段先问一句。读者已经知道问题，或标题已经提出问题时，直接解释机制。删除“沿这个拆法继续想”“还记得前面……吗”这类没有增加信息的铺垫。
- 一个例子说清当前机制即可。再次使用同一场景时，要推进到新的状态、约束或决策；不重新复述场景，也不另补一个只证明相同结论的例子。
- 技术深度来自对象、动作、因果和证据，不来自段落数量。正文保留理解主线所需的机制与限制；只有实现时才用到的修订协议、重连等细节，可移到文末或后续文章，不自动给每节追加生产化建议。
- 条件与限制紧跟对应结论，讲清一次即可。会改变结论的边界不能省，例如“本地取消不等于远端回滚”；无关当前问题的例外无需穷举。
- 表格、流程和图片已经表达的关系，正文只解释难点或取舍，不逐项再翻译一遍。缩短句子、增加加粗或拆成列表，都不能替代内容去重。

## 标题与排版

- 标题对应文章实际问题。默认作者常用“技术名 + 具体问题”、系列名加本篇问题，或口语化疑问；不限制为固定句式。
- 长篇 Markdown 通常使用一个 H1，主体按需要设置 H2；大章节标题默认不加序号，系列标题中的篇次保留。确有从属关系时再加 H3。局部改写保持原有合理层级，不为了套格式重排全文。
- 小节标题尽量能看出结论或疑问，不能只靠标题制造转折。
- 中文与英文、数字之间留空格，如 `Java 21`、`WebSocket 消息`。
- 类、方法、字段、命令和路径使用行内代码；术语采用常见写法，首次出现的陌生缩写按读者需要解释。
- 两个及以上平级观点、选项或配置项，用无序列表；有先后顺序或依赖关系的步骤，用有序列表。不能因为都属于同一主题就编号，也不要把并行关系写成步骤。系列篇次等本身有顺序的内容可保留编号。完整推理仍用连贯段落，对照信息适合表格。
- 加粗用于少量需要定位的判断。中文引号、顿号和破折号按语义使用，不作机械禁用。

## 引用与参考链接

默认作者希望正文连续阅读，不在每段末尾堆文档链接，也不给仅仅提到的产品名加超链接。

- 直接引用原文，或明确归属于某个来源的具体观点、数据和图表，在引用前后补来源链接。同一处引用给一次即可，不在后续复述中重复挂链接。
- 用于调研、核验机制和补充阅读的其他资料，集中放在文末“参考资料”，用无序列表去重列出。链接标题写明来源和主题，不写裸 URL，也不只写“这里”“官方介绍”。
- 移动链接时保留必要的来源归属和版本限定，不把外部结论改写成作者亲历。参考资料只收录本篇实际使用的公开来源；公开文章不链接读者无法访问的本地 Markdown、内部架构文档或私有路径。需要依赖这些材料时，在正文中交代必要信息或使用获准公开的图。
- 图注来源通常一个简短链接即可。不附例行查阅日期、长段免责或重复解释；会影响理解的限定放在对应正文讲清。用户明确要求“感兴趣可看”的延伸阅读，可保留在相应小节，不强行移到文末。

例如，介绍 LiteLLM 配置时，正文写配置与取舍，相关文档放入“参考资料”；引用 Seed 原话时，在引用块前后保留原文链接；采用 LiveKit 对比表时，在图注保留来源链接。

## 口语化表达，技术文章结构

口语化是措辞和语气的选择，不等于把技术说明写成连续聊天。关键机制需要让读者能定位问题、处理过程和适用边界；按这些信息之间的关系组织正文，不靠反复表态或提问串联段落。

按信息关系选择表达方式，不把长段落一律拆成圆点列表，也不要求每节使用同一套排版：

| 信息关系 | 适合的写法 | 使用边界 |
| --- | --- | --- |
| 场景、用户原话、外部引文 | 引用块，正文再分析 | 假设场景明确标注为例子；外部引文保留来源，不能混作作者亲历 |
| 平级观点、备选方案、配置项 | 无序列表 | 例如 Function Calling 与远程 MCP 是两种接法，用圆点并列；不暗示先后依赖 |
| 有先后依赖的处理或排查 | 编号列表，或“第一步：……”这样的加粗段首 | 写清每步的对象、动作与结果；并发分支不要写成串行步骤，不固定步骤数 |
| 状态、职责、方案的对照 | 用相同维度组织表格 | 比较项确实可对齐时再用；解释因果的长段落不硬塞进表格 |
| 输入输出、流转和分支 | 短关系用文字箭头，复杂关系用流程图或架构图 | 区分顺序、并发与条件；图后解释取舍，不再完整复述一遍图 |
| 定义、关键区别、适用边界 | 少量加粗，必要时独立成段 | 加粗帮助定位，不把整段加粗；斜体按语义选用，不为凑格式添加 |
| 独立补充或主题切换 | 子标题、留白，必要时分隔线 | 已有标题能分清时，不重复堆叠分隔；不用排版代替承接 |

介绍、因果推导、转折和个人理解仍然可以用连贯段落。问题在于把场景、机制、例外、建议都挤在同一段，或连续堆成读者找不到重点的说明。遇到这类内容，先分清关系，再决定哪里需要步骤、对照或强调，不能只添加符号。

例如，讲“旧请求在打断后返回”时，可以先用短场景交代乱序，再按实际先后解释标记回复、失效旧标识和检查迟到结果，最后单独说明框架范围与业务副作用。这只是结构选择示例，不要求每节照搬。

论证怎样推进见 [研究型文章写法](sincerelyplz-research-writing.md)；套话识别和修改检查集中在 [二次审校](human-writing-audit.md)，本文件不另维护禁用词表。
