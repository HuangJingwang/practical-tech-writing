# Sincerelyplz：研究型技术文章写法

这是本 Skill 的默认行文参考，用于 Sincerelyplz 发布的中文技术文章。用户明确指定另一位作者、平台语气或正式文风时，以新要求为准。它不替代事实核验和代码准确性。

## 文章怎么往前走

把文章写成研究过程，不写成先给结论再解释的说明书。一个核心小节通常按这个顺序推进：

1. 从正在做的模块、一次调用、一个报错或一个产品动作切入。
2. 直接提出问题，例如“这里有一个问题”“那问题来了”。
3. 给最小场景，让人物、资源或数据一步一步变化。
4. 用代码、请求、源码、日志或官方材料解释机制。
5. 写出极端情况、失败路径或当前方案的局限。
6. 落到“我们当前为什么这样做”，并把还没解决的问题留在原处。

不要强行让每一节都套满六步。只有存在明确的方案比较、源码追踪或边界条件时才展开；简单的配置说明可以直接进入命令和验证结果。

## 举例

- 先交代前提，再讲变化。不要一上来把概念、结论和反例揉在一段里。
- 例子中保持对象少且稳定，例如一个用户、一篇文档、一次分页查询、一组关系。
- 每一步只引入一个新条件：先说明正常情况，再改一个数据量、权限比例、并发动作或关系，解释结果为什么变了。
- 用极端情况验证边界。比如用户需要一页 10 条结果却几乎没有权限；Proposal 生成后另一位协作者编辑了同一块文档；递归关系重新走回已访问路径。
- 例子结束后必须回扣实现：它说明哪段代码、哪个数据结构或哪条方案边界。没有回扣的例子删掉。

## 列举方案

先说清共同问题和比较维度，再列方案。每个方案至少回答：

1. 它具体怎么做。
2. 在什么数据量、权限比例或业务前提下可以用。
3. 它会在什么情况下变慢、出错或增加维护成本。

列表里的项目必须在同一个维度上并列。不要写“优点、实践建议、未来规划”这种不平行的三项。方案比较结束后再给当前取舍，不能只写“方案 A 更灵活”。

## 怎么说明代码和资料

- 代码前先写为什么要看这段，例如“真正的数据是三元组，Model 转成图以后怎么参与鉴权？”
- 只贴能推进当前问题的调用、分支或数据结构；代码后解释它回答了什么，不能逐行翻译。
- 研究通常可以沿“官方文档 → GitHub 源码 → Issue / Discussion / 演示 → 当前判断”推进。每往前一步，交代上一步还缺什么答案。
- 找不到直接证据时，写成“我倾向于”“这里更像是”“我目前的判断”，不要把推测写成事实。

## 语言和节奏

- 以第一人称口语叙述研究过程。可以写“我当时想”“我去看源码时发现”“说了半天”。
- 问题直接落地：写“这里有一个问题”，不要写“这里有一个很现实的问题”；写事实，不替读者加“值得注意”“很关键”“很有意思”的感受标签。
- 允许适量的“那问题来了”“说实话”“哥们”一类表达，但它们后面必须有新信息，不能替代分析。
- 一个段落只推进一个动作或判断。场景和反问可以短，原理和边界可以长。
- 保留作者明确的判断和取舍；不要补宏大开场、励志结尾、均匀排比或“不是 X，而是 Y”的对称句。

## 写完后的检查

逐节检查：

- 开头能否指出一个具体动作或问题，而不是只讲技术背景？
- 场景里有没有可跟随的对象和变化？
- 每个方案或源码段是否解释了代价、失败条件或适用范围？
- 结论是否来自前面的资料、代码或例子？
- 是否删掉了“很现实、很关键、值得注意、有意思”等空泛修饰？
- 读起来是否像工程师在讲这次怎么查、怎么试、最后先怎么落地？
