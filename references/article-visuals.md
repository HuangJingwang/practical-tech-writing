# 文章配图与技术图规范

这份规范用于中文技术文章的配图规划、生成、绘制和审校。目标不是让文章“每一节都有图”，而是让读者少记一些抽象名词，多看懂一层关系。

## 配图的职责与优先级

一张图只能有一个主要任务。先写出这张图要回答的问题，再决定画法。

按文章可信度和解释能力，优先级通常为：

1. **真实证据**：产品截图、运行结果、GIF、日志、Trace、监控曲线、压测数据。
2. **确定性技术图**：架构图、流程图、时序图、状态图、数据流图、部署图。
3. **代码和配置**：最小但完整的关键实现。
4. **氛围图**：用角色和隐喻表现判断、矛盾、转折或章节气氛。

真实证据不能被插画替代。比如文章声称“任务必须确认后才创建”，最有说服力的是 Proposal 卡片和确认后的任务结果；氛围图只能帮助读者记住“先提议，再执行”这个概念。

以下情况通常不画图：

- 一个动作、两个对象、两三句话已经讲清楚。
- 只是重复正文标题和关键词。
- 图中只能放一堆泛化图标，没有新的关系。
- 没有证据支持图中的组件、顺序或结论。
- 为了凑数量而给每个 H2 配一张图。

## 先做配图计划

文章结构稳定后、生成图片前，先列配图计划。每张图至少写清：

| 字段 | 要回答的问题 |
| --- | --- |
| 放置位置 | 放在哪一段之后，为什么放这里 |
| 读者问题 | 读者看完上一段最可能卡在哪里 |
| 图的职责 | 证据、结构、顺序、状态，还是氛围 |
| 图型 | 截图、GIF、架构图、流程图、时序图、状态图、数据图、氛围图 |
| 核心元素 | 必须出现哪些组件、角色、状态或数据 |
| 关系 | 箭头方向、调用顺序、包含关系或前后变化 |
| 可见文字 | 图中真正需要出现的短标签 |
| 依据 | 代码、接口、日志、产品行为、官方文档或作者说明 |
| 图前引导 | 正文提醒读者重点看什么 |
| 图后结论 | 读者从图里应该得到什么判断 |
| 输出文件 | 文件名、格式、尺寸和保存位置 |

默认先交付这份计划，不自动消耗时间批量生图。用户明确要求完整配图或生成图片后，再制作资产。

## 怎样选择图型

| 读者真正想知道的事 | 首选图型 |
| --- | --- |
| 系统由哪些部分组成，谁依赖谁 | 架构图 |
| 一条请求依次经过哪些步骤 | 流程图或 Pipeline 图 |
| 多个参与方按时间如何交互 | 时序图 |
| 对象会经历哪些状态，什么事件触发变化 | 状态图 |
| 数据从哪里来，在哪里转换、存储和输出 | 数据流图 |
| 服务运行在哪里，进程和基础设施怎么部署 | 部署图 |
| 两个方案的职责、成本和边界有什么不同 | 对照表，必要时配并列结构图 |
| 页面最终长什么样、功能是否跑通 | 截图或 GIF |
| 错误到底发生在哪一层 | Trace、日志片段加调用链 |
| 性能、延迟、吞吐如何变化 | 数据图，并交代测量环境 |
| 一个观点、矛盾或转折需要被记住 | `visual-ip-illustrations` 氛围图 |

不要把所有关系塞进“总架构图”。空间关系、时间顺序和状态变化是三种问题，通常应拆成不同的图。

## 技术架构图的画法

### 先确定抽象层级

一张架构图只选一个层级：

- **上下文图**：用户、当前系统、外部系统。用来交代文章范围。
- **容器或服务图**：前端、后端、Agent 服务、数据库、消息系统、第三方平台。适合讲总体方案。
- **组件图**：某个服务内部的 Router、Processor、Repository、Adapter。适合讲实现细节。
- **部署图**：进程、Pod、节点、网络区和第三方基础设施。适合讲运行方式和故障域。

不要在一张图里同时放“用户”“Kubernetes Pod”“Java 方法名”和“数据库字段”。层级混在一起，读者无法判断每个方框的粒度。

### 从一个问题开始

图标题写成能回答问题的短句，例如：

- `Voice Agent 怎样加入现有会议`
- `一次 MCP 调用经过哪些服务`
- `Proposal 为什么不会直接写入业务数据`

不要使用无法限定范围的标题，如“系统架构”“整体流程”“核心原理”。

### 先列事实，再开始摆框

绘图前先从代码、接口或作者提供的信息中列出：

1. 参与组件及其真实名称。
2. 每个组件在本图中的单一职责。
3. 每条调用的发起者和接收者。
4. 传递的核心数据、协议或事件。
5. 同步、异步、长连接或广播方式。
6. 外部依赖、人工确认点和失败出口。

无法确认的关系不要画成实线事实。必要时使用“方案推测”说明，或者从图中删除。

### 布局规则

- 主链路默认从左到右；上下方向只表示层级、分支或异步回传。
- 用户或输入放在左侧，结果或外部影响放在右侧。
- 同一运行边界放进带标题的容器，例如 `Meeting Client`、`Java Backend`、`Pipecat`、`External Services`。
- 对称不是目标。主链路要最直，失败路径和辅助链路可以放在下方。
- 尽量避免线交叉；需要跨越时调整组件位置，不靠更多颜色补救。
- 一张正文图建议保留 5～9 个主要节点。超过 12 个节点时，优先拆图。
- 图四周保留空白，组件之间的距离要能容纳箭头标签。

### 组件和标签

- 方框使用名词：`Meeting Client`、`Pipecat`、`MCP Server`。
- 箭头使用动词或数据：`发送 PCM`、`调用工具`、`WebSocket 推送 Proposal`。
- 组件框内最多放“名称 + 一句职责”，不要写一段说明书。
- 使用正文和代码里的真实名称。正文写 `document_edit_router`，图里不要突然改成 `Doc Agent`。
- 技术名词使用等宽字体或明确区分，中文解释保持简短。
- 协议只有在影响设计时才标，例如 `WebSocket`、`HTTP/SSE`、`Agora RTC`；不要给每根线都补一串实现细节。

### 箭头语义

同一张图中，线型必须固定含义：

- 实线：同步调用或主要数据流。
- 虚线：异步通知、可选路径或控制信号。
- 双向箭头：确实存在双向传输，不能用来含糊表示“有联系”。
- 回环箭头：重试、反馈或持续流，必须标出触发条件。

箭头必须有方向。不要使用没有说明的连线，也不要让箭头从“数据库”主动指向业务服务，除非确实存在订阅或回调。

### 颜色语义

技术图控制在 3～5 个语义颜色内，并在全文保持一致。例如：

- 蓝色：作者控制的核心服务。
- 灰色：客户端或基础设施。
- 紫色：模型或 Agent 处理。
- 绿色：业务写入成功或已确认结果。
- 橙色：人工确认、警告或外部依赖。
- 红色只用于失败、拒绝和高风险路径。

不要按“每个框一个颜色”上色。颜色必须能帮助读者分类。

### 边界和失败路径

架构图至少检查以下边界：

- 当前文章负责讲到哪里，哪些属于既有系统。
- 哪些组件由团队控制，哪些是第三方服务。
- 哪个位置持有用户身份或 Token。
- 哪个位置允许写业务数据。
- 哪一步需要用户确认。
- 超时、拒绝、无权限或下游不可用时走向哪里。

失败路径不一定全部画进总图。对文章结论有影响的失败必须出现；其余可以另画局部流程图。

### 架构图输出方式

- 简单、稳定、以关系为主：优先 Mermaid，正文和版本库容易维护。
- 需要精确排版、分组、图标和后续编辑：优先 `.drawio` 或其他可编辑矢量源文件，同时导出 PNG/SVG。
- 需要在 FigJam 讨论：使用 diagram 工具生成草图，再保留可编辑版本。
- 不使用生图模型生成真实架构图。它容易写错文字、丢箭头、改变方向，也无法保证下一次修改仍与代码一致。
- 交付时同时保留源文件和发布文件。Markdown 引用 PNG/SVG，源文件放在同一资产目录。

## Pipeline 与流程图

Pipeline 图强调**处理顺序和分支**，每个节点使用动作或处理器名称。

以 Agent Pipeline 为例，先画主链路：

```text
音频输入 → STT → 聚合用户上下文 → 业务分流 → LLM → TTS → 音频输出
```

再按真实实现补充：

- 哪些节点接收原始音频，哪些接收文本或 Context。
- 节点输入和输出分别是哪类 Frame、事件或 DTO。
- 分支处理完以后是否回到主链路。
- 哪个分支会提前消费当前请求，不再调用后面的 LLM。
- 打断、取消、错误和超时如何停止旧任务或恢复主链路。

流程图形状保持简单：

- 圆角矩形：开始、结束或外部触发。
- 矩形：处理动作。
- 菱形：真正存在的判断条件。
- 文档或数据库形状：确实涉及文档、持久化时才使用。

不要把每个方法调用都画成判断框。分支标签写条件，例如 `proposed`、`no_active_document`，不要只写含糊的“是/否”。

适合拆图的信号：

- 主链路超过 8～10 个处理节点。
- 正常路径和失败路径交叉三次以上。
- 一张图同时想解释媒体流、工具调用和业务写入。

## 时序图

时序图用于回答“谁先调用谁”和“什么时候返回”。参与者按调用关系从左到右排列，时间从上到下。

绘图规则：

1. 只保留当前用例涉及的参与者。
2. 消息名使用动词，必要时带核心参数或结果。
3. 同步返回画返回线，异步通知明确标注 `async`、事件名或通道。
4. 用 `alt` 表示互斥分支，用 `opt` 表示可选动作，用 `loop` 表示真实循环。
5. 用户确认要作为一个明确参与动作出现，不能藏在服务内部。
6. 超时和异常只保留影响读者理解的分支。

一个 Proposal 用例可以按以下骨架展开：

```text
用户 → Voice Agent：提出创建任务
Voice Agent → MCP：生成 Proposal
MCP → 业务服务：校验范围并保存待确认数据
业务服务 --WebSocket--> Meeting Client：推送 Proposal 卡片
用户 → Meeting Client：确认
Meeting Client → 业务服务：执行创建
业务服务 → Meeting Client：返回结果
```

如果正文在讲打断，应另画音频打断时序，不要把 Proposal 和 `InterruptionFrame` 塞进同一张图。

## 状态图和生命周期图

状态图中的框表示“对象当前处于什么状态”，箭头表示“什么事件让状态改变”。状态名使用形容词或过去分词，事件使用动词。

例如 Proposal 生命周期：

```text
drafted → proposed → confirmed → executing → applied
                   ↘ rejected
                   ↘ expired
executing → failed → retrying / cancelled
```

绘制时补齐：

- 初始状态和终止状态。
- 用户操作、系统事件和超时事件。
- 是否允许重试、撤销或重复确认。
- 状态是否跟随会议、会话、请求或文档生命周期。
- 刷新页面、断线重连、服务重启后状态存在哪里。

不要把步骤名当状态，例如“调用接口”“发送消息”属于动作，不是状态。

## 数据流、鉴权与信任边界

涉及 Agent、MCP、第三方模型和内部业务服务时，至少回答：

1. 原始数据是什么：音频、视频帧、字幕、文档、用户输入。
2. 数据在哪里被裁剪、聚合、脱敏或转换。
3. 哪些数据会发送给第三方模型。
4. Token 在哪里签发、传递和校验。
5. 哪个服务根据 Token 恢复用户与会议范围。
6. 权限判断和业务写入分别发生在哪里。
7. 日志是否可能记录 Token、文档正文或用户数据。

画法：

- 用带标题的虚线框表示信任边界，如 `Client`、`Internal Network`、`Third-party Model`。
- 箭头标注数据类别，不在图中放真实 Token、URL、用户姓名或公司信息。
- 鉴权箭头与业务数据箭头可以使用不同线型，但必须给出图例。
- 如果 Pipecat 只拿会话 Token，图里就画 `MCP Session Token`，不要虚构用户名、组织信息或登录 Cookie。
- 权限校验点使用锁形标记或短标签，不把“有 Token”写成“已经有权限”。
- 对投屏、网页或文档里的文字标注“不可信输入”，与系统指令分开。

## 截图、GIF、日志和数据图

### 截图

- 截图证明真实界面、交互状态或错误现象。
- 裁掉浏览器标签、无关桌面和调试窗口，只保留论点所需区域。
- 发布前检查姓名、头像、会议标题、公司、域名、Token、内部地址和真实业务数据。
- 马赛克要覆盖完整，不保留可识别边缘；更稳妥时使用专门测试数据重新截图。
- 一个截图只证明一个结论。需要对比时使用相同尺寸的前后两张，或明确标出关注区域。
- 不用插画重画真实产品截图，也不把设计稿当成已实现结果。

### GIF

- GIF 用来表现 3～15 秒内可重复理解的交互，例如 Proposal 出现、确认、任务落库或文档 Diff。
- 剪掉等待、登录和无关鼠标移动；开头直接出现操作起点，结尾停留在结果状态。
- 循环播放时首尾不要产生明显跳变。
- 控制尺寸、帧率和文件大小，文字必须在文章宽度下仍可读。
- 上传后检查平台是否保留多帧动画。不能只看 `.gif`、`.webp` 或 `.awebp` 后缀；要在最终预览或发布页验证是否真的播放。
- 平台把 GIF 变成静态图时，重新上传原始 GIF，不从图片预览复制粘贴；仍失败则使用平台支持的视频方式或放静态关键帧加演示链接。

### 日志和 Trace

- 只截包含错误起点、关键调用和根因的最小片段。
- 隐去 Token、Cookie、UID、内部域名、IP、文件路径和用户数据。
- 用短注释指出时间顺序、错误码和真正失败的层，不在图片外做毫无对应的猜测。
- 日志很长时用文本代码块，截图只保留能证明视觉上下文的部分。

### 数据图

- 标注指标、单位、样本量、测试环境和时间窗口。
- 坐标轴从能诚实展示差异的位置开始；截断坐标轴必须明确说明。
- 没有实测数据时不用精确曲线或百分比装饰文章。
- 对比方案保持同一量纲、同一环境和同一统计口径。

## Visual IP 氛围图

`visual-ip-illustrations` 在这套写作流程中只负责氛围图和概念隐喻图。它适合表现：

- 作者遇到的阻力、困惑、转折和新的判断。
- “从记录信息到真正干活”这类抽象变化。
- 一段流程的概念隐喻，例如过桥、分流、打包、守门、校准。
- 长篇技术内容中章节之间的视觉换气。

它不适合表现：

- 真实组件和服务之间的调用关系。
- 精确的 Pipeline 顺序、协议、参数和 Frame 类型。
- 鉴权、权限边界、状态机、部署拓扑和故障链路。
- 产品已经实现的界面或运行效果。
- 需要逐字准确的密集标签、代码、日志或数据。

需要氛围图时，明确调用 `visual-ip-illustrations` 并遵守它自己的路由、角色、版权、提示词、QA 和保存规则。写作流程只额外约束：

1. 先从正文选一个“认知锚点”，不要只拿章节标题生图。
2. 一张图只表达一个判断或隐喻。
3. 角色必须实际执行核心动作，移除角色后概念不能仍然完整。
4. 默认使用 16:9 横向正文图；不把正文图拉伸成封面。
5. 同一篇文章固定一个 Visual IP 路线、配色和线条语言。
6. 图中文字控制为少量短标签，并复制正文中的真实用词。
7. 氛围图前用正文交代它映射的实际问题，图后回到技术事实。

默认路线由 `visual-ip-illustrations` 自己决定；用户指定 Xiaohei、Littlebox 或其他路线时，以用户选择为准。涉及受保护角色、来源、商标或公开发布边界时，严格遵守对应路线的引用和授权要求。

氛围图不能画成披着手绘皮肤的架构图。出现多个真实服务名、方向箭头、协议、数据库和分支条件时，切回确定性技术图。

## 封面图

封面图和正文氛围图是两个资产：

- 先确认平台实际槽位比例，再生成封面。不能用方图上传到横向槽位后依赖平台拉伸。
- 掘金文章封面和专栏封面可能使用不同比例，以当前编辑界面显示的槽位为准。
- 标题在缩略图尺寸下仍要读得清，封面只保留一个主标题和一个主要动作。
- 封面可以使用通用生图能力；不要强迫 `visual-ip-illustrations` 承担它明确排除的海报或封面任务。
- 封面不承担技术细节，不画密集 Pipeline 或小字号代码。
- 生成后检查像素尺寸和宽高比，再上传原图；不要截图、复制预览或手工拉伸。

## 图片位置、文字和尺寸

### 正文位置

图片放在首次需要它的位置，不在文章末尾集中展示。

图前写一句“看什么”，例如：

> 下面这张图先看音视频怎么进出 Pipecat，业务工具调用暂时不放进来。

图后写一句“得到什么”，例如：

避免：

- “架构如下图所示”后没有解释。
- 图片和正文讲的是两套命名。
- 图先出现，隔几段才说明用途。
- 连续放三张图，中间没有任何阅读引导。

### 图中文字

- 只保留读者必须在图内看到的词。
- 组件名、状态名、协议和箭头标签逐字检查。
- 中文与英文保持全文一致，例如 `Voice Agent`、`WebSocket`、`MCP Session Token`。
- 说明性长句放在正文或图注，不塞进方框。
- 图中文字最小字号按文章最终显示宽度检查，不能只看原图放大效果。

### 比例

- 技术正文图默认 16:9；节点较多或纵向时序较长时可使用 4:3 或纵向图。
- 氛围图遵循 `visual-ip-illustrations` 的 16:9 正文图规范。
- 截图和 GIF 以内容可读为先，不强行裁成统一比例。
- 封面先量平台槽位，再按该比例重新构图；不得通过 CSS 或上传框拉伸。


规则：

- 使用两位数字保持正文顺序，英文短名说明图片内容。
- 技术图保留可编辑源文件；发布图片使用 PNG 或 SVG。
- 不覆盖用户已有素材；新版本使用 `-v2`、`-v3`。
- 用户明确要求不放进项目时，放到用户指定目录，例如桌面文章资产目录。
- Markdown 使用相对路径时，确认发布平台能够上传本地资产；平台链接生成后再替换。
- Alt 文本描述图在证明什么，不只写 `image.png`。

## 发布前检查

### 技术正确性

- 图中组件来自真实代码、接口、日志、设计或经过核对的官方资料。
- 箭头方向、协议、同步/异步、输入输出和正文一致。
- 图没有把推测画成已经实现的事实。
- 正常路径、关键失败路径、用户确认和写入边界没有被美化掉。
- 图中的权限判断位置与真实系统一致；持有 Token 不等于通过权限校验。
- Pipeline 节点顺序与代码一致，提前消费、旁路、重试和打断已经交代。
- 时序图的先后顺序能被真实调用链支持。
- 状态图有初始、终止、拒绝、失败或过期等必要状态。

### 视觉可读性

- 缩到文章正文宽度后，标题、节点和箭头仍清楚。
- 主链路能在 3 秒内找到，图的视觉中心与正文重点一致。
- 颜色有固定语义，色盲或黑白打印时仍能靠形状、线型和文字区分。
- 没有线条穿过文字、箭头交叉、边界框压住组件或图例缺失。
- 中英文、大小写、空格、类名、协议名和状态名无误。

### 证据与隐私

- 截图、GIF、日志、URL 和文件名已脱敏。
- 没有 Token、Cookie、内部域名、用户姓名、公司信息和真实业务数据。
- GIF 在最终平台预览中确实会动。
- 数据图注明了单位、环境、样本量和时间窗口。
- 氛围图没有被当成实现证据，技术图没有使用生成模型猜测关系。

### 文章连贯性

- 每张图前有观察重点，图后有结论。
- 图片出现的位置就是读者第一次需要它的位置。
- 删除任何一张图后，如果文章信息毫无损失，这张图应当删除。
- 同一概念在正文、代码、图和图注中使用同一个名字。
