# 文章结构选择

以下内容是推理顺序，不是必须照抄的小标题。根据文章的具体结论把 `背景`、`方案`、`总结` 改成有信息量的标题，避免整篇只剩模板骨架。

## 业务实战 / 故障复盘

适合 WebSocket 丢消息、数据库慢查询、并发问题、线上异常。

1. 交代模块、现象、影响和为什么值得处理。
2. 用时间线、日志或最小复现描述问题怎么出现。
3. 写一开始的排查假设，以及哪些被证据排除。
4. 解释真正原因，不跳过关键因果。
5. 先给设计约束，再给代码或配置。
6. 交代性能、失败路径、回滚、监控和未覆盖场景。
7. 收束结论并列出参考。

不要为了戏剧性虚构事故、损失、老板对话或线上数据。

## 原理拆解 / 源码学习

适合 JVM、Pulsar、BookKeeper、Transformer、索引或协议。

1. 从一个具体疑问或前置文章留下的坑切入。
2. 给一张概念总览或分层表，说明本篇边界。
3. 按数据流或调用链拆核心步骤。
4. 单独解释容易混淆的概念。
5. 用公式、伪数据、源码片段或小实验验证。
6. 回到真实使用场景，说明理解原理能解决什么问题。
7. 总结架构、训练/运行时或设计/实现之间的边界。

## 方案选型 / 观点文章

适合“为什么不推荐 X”“X 和 Y 怎么选”。

1. 交代自己的业务目标与硬约束。
2. 公平说明候选方案原本解决的问题。
3. 给出采用或放弃的证据：文档、源码、PoC、迁移成本或实际限制。
4. 按约束逐项比较，避免先有结论再找材料。
5. 写清楚反例：在什么场景下，被否定的方案反而合适。
6. 给出当前选择，以及还没有解决的风险。

观点可以鲜明，证据和边界必须跟上。

## 项目展示 / 工具开发

适合插件、自动化工具、AI 应用或个人项目。

1. 从自己反复遇到的麻烦切入。
2. 明确目标与不做什么。
3. 展示最终使用流程或结果。
4. 说明技术选型，只展开真正影响实现的决策。
5. 讲 2～4 个核心实现点，配可运行代码。
6. 写踩坑、限制、安装/运行方式和仓库链接。
7. 总结目前是否真的解决了原问题。

不要把功能清单写成广告文案。

## 好奇心驱动的科普

适合“朋友发来一个网站”“某个现象为什么会发生”。

1. 用真实小故事或现象开场。
2. 提出读者也会问的核心问题。
3. 通过一次小实验排除直觉误解。
4. 拆解背后的协议或机制。
5. 使用一个贴切比喻，再马上补回准确技术定义。
6. 说明这个机制能证明什么、不能证明什么。
7. 总结与参考。

比喻负责帮助理解，不能代替技术解释。
