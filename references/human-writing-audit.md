# 二次审校：检查什么，改到什么程度

本文件用于完稿后的检查与修改强度选择。事实、用户风格和交付范围见 [主文件](../SKILL.md)。自然度检查不用于判断作者身份，也不以绕过检测器为目标。

## 先分清问题严重程度

**需要修正或明确指出**：事实或来源不支持结论，前提缺失，逻辑自相矛盾，技术名词错误，明显病句，以及偏离用户指定范围或风格。

**按效果取舍**：段落长度、个别连接词、标题形式和修辞。默认作者已明确排除的长段反问、连续设问和自问自答按风格失配修正，执行 [直接陈述规则](style-guide.md#直接陈述避免连续设问)。单个词不等于写作问题，不为统一形式重写已经自然的段落。

## 检查论证是否推进

- 能否用一句话说清文章要回答的问题？各段是否提供了新的事实、解释、例子、比较或判断？重复同一结论的段落可以合并。
- 前文提出的麻烦，后文是否回答了？方案之间的连接有依据，还是为了“演进”硬造缺陷和替代关系？
- 机制能否支持后面的结论？方案选择是否说明了条件和需要承担的代价？
- 对应有先后关系的段落，可试着调换位置检查承接。正常的并列比较可以互换，不因此判成结构错误或强行制造因果。
- 例子或比喻是否解释了当前机制？删掉以后不影响理解的故事、铺垫和装饰，可以删减。

## 集中扫描套话和低信息表达

以下是检查线索，不是禁词表。只有它们造成空泛、歧义、重复或风格失配时才改。

| 现象 | 常见表达 | 修订方向 |
| --- | --- | --- |
| 意义膨胀 | “具有重要意义”“标志着关键转折” | 写清具体改变、对象和后果 |
| 宣传口吻 | “无缝”“强大”“领先”“颠覆性” | 用能力、条件或依据替代笼统评价 |
| 模糊归因 | “业内普遍认为”“大量实践证明” | 按主文件的事实要求补来源或限定判断 |
| 模板对偶 | “不是 X，而是 Y”“不仅 X，更 Y”“这样既能……也能……” | 默认作者不使用这类套式概括收益；直接说明需求、做法与具体结果 |
| 空泛个人转折 | “这让我更关注……”“这也让我意识到……” | 默认作者直接写实际需求、选择和理由，不靠一句心理转折补作者声音 |
| 固定凑数 | 每节固定三点、每点等长 | 按真实比较维度和信息量组织 |
| 戏剧化碎句 | “没有报错。没有告警。一切正常。” | 没有叙事必要时合成自然句子 |
| 口号或故作轻松 | “看不见，就修不好”“就这么简单” | 说明可以核对的行为和边界 |
| 空反问与通用结尾 | “这意味着什么”“未来可期” | 直接给出判断，或结束在实际问题上 |
| 连续设问与隐含问句 | “要不要……哪些……什么时候……”“谁来……再让谁……” | 检查整段和列表，不只找问号；改为主体对具体对象的处理、配置或控制，保留真实未知项 |
| 替读者预判 | “很现实”“值得注意”“令人惊讶” | 让后面的事实体现其影响 |
| 抽象或翻译腔 | “复杂性得到了降低”“接住反馈” | 改为具体主体做了什么；保留准确的惯用表达 |

默认作者改写示例：

不采用：“这让我更关注一种组合。这样既能追求自然对话，也能保留已有工具。”

采用：“我们已经有文字入口，没必要为了语音再做一套 Agent。打字和说话都交给同一个业务 Agent，工具和上下文继续共用。”

这类改写的重点是已有条件和实际需求，不能把示例中的项目事实移植到另一篇文章。

## 检查冗长与重复

Pipecat 文章修订中出现的问题，是同一机制在多个小节重复解释、解释前铺垫过长、每个结论后继续追加限制和建议。不能只把长句改短，否则文字变碎，信息总量仍然没有减少。

| 问题 | 判断方法 | 处理方式 |
| --- | --- | --- |
| 同义复述 | 后一段是否只是把上一段结论换一种说法？ | 合并，保留信息更具体的一处 |
| 小节职责重叠 | 两节是否都在解释同一机制，而不是不同问题？ | 指定主要解释位置；其余只讲新增关系，必要时撤掉小节 |
| 铺垫比结论长 | 标题已提出问题，正文是否又反问、回顾、假设一轮？ | 直接回答；仅保留理解机制所需的场景 |
| 图表后重复讲解 | 正文是否按原顺序复述图表每一项？ | 留下图表不能直接说明的因果或取舍 |
| 边界与建议堆积 | 每段是否都追加“还需要”“不能认为”“应用应该”？ | 合并同一限制；影响结论的就地保留，实现细节移出主线 |
| 承接句重复两遍 | 上节结尾与下节开头是否解释了同一个问题？ | 选一处交代，另一处直接推进 |

**先删冗余，再调整排版。**对可疑段落依次判断：有没有新增信息？是否属于当前小节？删去后会不会丢失关键因果、条件或事实？没有新增信息就删，有信息但偏离主线就移动，承担机制解释的内容则保留并写清楚。不设机械字数上限，也不为达到压缩比例删技术细节。

例如，解释 Frame 的收益，可以直接写：

> Frame 统一了节点之间的数据格式。更换识别服务时，适配层仍然输出约定的转写 Frame，后面的聚合器就可以继续处理。

不必先问“换一家服务，后面的节点要不要全部跟着改”，再重复适配职责，最后补“我比较认同这种划分”。后续若讨论服务能力差异，再说明流式支持、时间戳等条件；不能把“减少改动”夸成“任何服务都可以直接替换”。这个例子用于说明压缩方式，不是所有文章都要使用的固定内容。

修改后检查相邻小节：重复定义是否仍在、承接是否断裂、图表是否还对应正文、关键限制和引用是否被误删。审稿给出具体位置与合并方向，不只评价“啰嗦”或“AI 味重”。

## 检查声音、节奏与边界

检查关键技术说明能否快速定位：问题是什么、机制怎样工作、哪些条件影响结论。若连续段落混放场景、步骤、状态和个人建议，按 [技术文章结构](style-guide.md#口语化表达技术文章结构) 重新组织；若已经清楚，不为统一格式强行改成列表。特别检查把并发写成“第一步、第二步”、整段加粗、引用块来源不明，以及只有口语承接却没有层次的情况。

按主文件检查知识与经历的归属：第一人称表达的是具体理解或取舍，还是把已有机制、通行做法包装成个人方法？改为客观表达后，可选建议是否又被误写成框架默认行为？检查归属和成立条件，不以“我”字多少判断文风。

连续多段起句、长度和结构相同时，检查是否模板化；不要反过来用错别字、无意义感叹或随机碎句制造变化。技术对象的名称保持稳定，没必要用同义词轮换。

图前引导和图后解释只留下有助于阅读的内容。不要求每张图前都写“下面这张图”，也不在图后重复一次标题。图的具体核验见 [配图规范](article-visuals.md)。

语言润色不默改引用和代码块。发现技术问题时单独指出，再按当前任务授权决定是否修正；不能用“保留原文”放过已发现的错误，也不能借审校扩展任务。

## 清理交付残留

按用户要求的交付形态检查，重点查助手话语、未完成的模板占位、内部引用标记、重复标题和无用的链接跟踪参数。示例代码中有意保留的占位值不要机械删除。

检查链接位置是否符合 [引用与参考链接](style-guide.md#引用与参考链接)：正文只保留实际引用前后的来源链接，普通产品名和段末补充阅读链接移到文末参考资料并去重。检查引用能否支持对应内容；对新增、修改或先前未核验的来源进行核对。已确认的资料不因一次局部润色全部重新研究。

## 选择修改强度

- 主线清楚、问题局部：定点修改，保留自然段落。
- 同一问题在若干段落重复：按段或小节整理，避免只换同义词。
- 推理断裂、主题散开或重复严重：在授权范围内重新组织结构。用户仅要求审稿时，报告问题和建议，不擅自改成全文重写。

修改后只需再检查受影响的论证、事实和表达，确认修正没有引入新问题。无需为了凑满固定轮数重复审校。
